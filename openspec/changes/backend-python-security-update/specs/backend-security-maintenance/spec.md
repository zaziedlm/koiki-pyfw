## ADDED Requirements

### Requirement: 更新証拠の追跡

- 【SHALL】担当者は、更新対象ごとに現行版・採用版・公式根拠・確認日・適用先・未完了項目を記録しなければならない。
- 【SHALL NOT】担当者は、同梱pipの更新とsslのCVE修正収録を同一の証拠で対応済みと判定してはならない。

#### Scenario: E1 正常系 - 収録証拠が揃う
- **WHEN** 採用する配布版で対象CVEの収録と適用先を確認する
- **THEN** 根拠URLと版と確認日を記録して対象を完了候補にする

#### Scenario: E2 異常系 - 修正版が未確認
- **WHEN** ssl修正がブランチにマージ済みでも配布版への収録を確認していない
- **THEN** Pythonのssl対策を未完了として記録する

#### Scenario: E3 境界値 - OSバックポート
- **WHEN** OSパッケージが上流修正版より小さい版番号で修正を提供する
- **THEN** 対象OSの勧告とパッケージrevisionで修正有無を判定する

### Requirement: 信頼と展開経路の維持

- 【SHALL】担当者は、Python・取得ツール・アプリ・OSの信頼ストアおよびBrotli展開経路を個別に確認しなければならない。
- 【SHALL NOT】担当者は、脆弱性対応のためにTLS検証を無効化してはならない。

#### Scenario: S1 正常系 - 信頼ストア反映
- **WHEN** 更新済み環境で正規TLS接続を行う
- **THEN** 検証を有効にしたまま成功し参照したCAとツールの版を記録する

#### Scenario: S2 異常系 - 不正な証明書
- **WHEN** 安全な隔離fixtureの不正チェーンを検証する
- **THEN** 接続を拒否し拒否結果と検証条件を記録する

#### Scenario: S3 境界値 - PythonのBrotli未導入
- **WHEN** PythonパッケージにBrotliが存在しない
- **THEN** Python側の非搭載を記録しOSライブラリとその他ランタイムの調査結果を別に判定する

### Requirement: 既存機能と反映確認

- 【SHALL】担当者は、更新前と同じ対象の単体・DB統合・DDL往復テストを専用DBで実行し、結果とスキップ理由を比較しなければならない。
- 【SHALL NOT】担当者は、新規失敗または未検証の適用先を残した状態で全体を完了と判定してはならない。

#### Scenario: R1 正常系 - 回帰検証成功
- **WHEN** 更新後に基準対象を再実行する
- **THEN** 新規失敗がなくロックと導入版が一致し結果を保存する

#### Scenario: R2 異常系 - 機能退行
- **WHEN** 更新後に新規失敗または未説明のスキップ増加を検出する
- **THEN** 次の更新を止めて原因と未完了タスクを記録する

#### Scenario: R3 境界値 - 設定済みでも実体未確認
- **WHEN** DockerやCIの版指定だけを更新して実行物を確認していない
- **THEN** 反映確認は未完了のままにする
