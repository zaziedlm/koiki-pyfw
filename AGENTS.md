## Core Rules

- Keep reusable framework behavior in `components/libkoiki/`.
- Keep reference application and business-specific behavior in `components/koiki_ref_app/`.
- Treat root `app/` as a compatibility wrapper unless explicitly maintaining legacy imports.
- Treat `apps/` as the downstream business backend layer; keep the reference frontend under root `frontend/`.
- When an API schema, status/error behavior, auth, Cookie/CSRF, or configuration changes, check the affected frontend contract as well as backend ownership.
- Prefer current implementation over historical design notes when they conflict.
- Treat `openspec/specs/` as the source of truth for intended behavior and current implementation as the source of truth for existing behavior; when they diverge, raise an `openspec/changes/` proposal rather than silently changing either.
- When writing or editing any OpenSpec artifact, follow `docs/agent/skills/koiki-spec-authoring/SKILL.md`. Its Japanese 【SHALL】 notation overrides the English SHALL prose that built-in `openspec-*` skills produce.
- Keep spec content under `openspec/`; keep the spec ledger and loop records under `.aidx/loop-design/`.
- Follow the existing layered structure unless there is a strong reason not to.
- Validate changes at the smallest scope that proves the behavior.

## Directory Intent

- `components/libkoiki/`: shared backend framework
- `components/koiki_ref_app/`: current reference application backend code
- `app/`: compatibility wrapper
- `frontend/`: frontend code
- `tests/`: unit and integration validation
- `openspec/`: capability specs and change proposals
- `.aidx/`: AI-driven development framework operations (spec ledger, loop records, cheat sheet)
- root `package.json`: developer tooling only (OpenSpec CLI). Application dependencies live in `pyproject.toml` and `frontend/package.json`.
