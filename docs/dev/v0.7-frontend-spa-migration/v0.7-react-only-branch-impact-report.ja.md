## 1. 概要

本ブランチは、`frontend/` を Next.js ベースの BFF(Backend for Frontend)構成から、
Vite + React Router によるピュアな SPA(Single Page Application)構成へ移行した。

移行の中心的な設計判断は次の 1 点に集約される。

> これまで Next.js サーバ層が担っていた「トークンの保管(httpOnly Cookie 化)・CSRF 対策・
> バックエンドへの代理呼び出し」を、FastAPI バックエンド自身が提供する
> **Cookie セッション認証契約(`/api/v1/auth/session/*`)** に置き換える。

この結果、フロントエンドは「静的ファイルの集合」となり、ブラウザは FastAPI と直接通信する。
バックエンドへの変更は**既存 API を一切壊さない追加(additive)**として実装されており、
従来の Bearer トークン API は従来どおり利用できる。

- 既存の Bearer トークン API(`/auth/login`、`/auth/refresh`、`/sso/login`、SAML 等)は

- 変更はすべて「ブラウザ SPA 向け Cookie セッション認証の追加」とそのための共通化に集中している。

## 4. フロントエンドの変更: Before / After

### 4.1 Before(main): Next.js BFF 構成

- **API route handlers 16 ファイル**(`src/app/api/**`): auth / todos / users / sso / saml の
  各リクエストを Next.js サーバが受け、Cookie から JWT を取り出して
  `Authorization: Bearer` に詰め替え、FastAPI へ代理送信していた。
- **`middleware.ts`**: `/dashboard` 等の保護ルートで Cookie の JWT 形状を検査しリダイレクト。
- **`next.config.ts`**: `/api/backend/:path*` の rewrite プロキシ、セキュリティヘッダ。
- **`lib/cookie-utils.ts` / `lib/csrf-utils.ts`**: Next.js サーバ側の Cookie 発行・CSRF 生成/検証。
- トークンは Next.js サーバが httpOnly Cookie として発行・保管していた。

つまり、**認証・CSRF・プロキシという「サーバの責務」が Node.js 側にもう 1 セット存在**していた。

### 4.2 After(HEAD): Vite + React SPA 構成

- **配信**: `nginx-unprivileged`(ポート 8080)による静的ファイル配信。
  `try_files ... /index.html` の SPA フォールバックと `/health` のみ(`frontend/docker/nginx.conf`)。
- **ルーティング**: `react-router-dom` v7 の `BrowserRouter`(`src/App.tsx`)。
  ルート保護はクライアント側ガード(`src/components/auth/auth-guard.tsx`)。
- **API クライアント**: `src/lib/cookie-api-client.ts` が `credentials: 'include'` で
  FastAPI を直接呼ぶ。Bearer ヘッダは付与しない(Cookie は httpOnly で JS から読めない)。
- **CSRF**: `/auth/session/csrf` からトークン取得 → `x-csrf-token` ヘッダで送信。
  `CSRF_TOKEN_INVALID`(403)時はトークン再取得して 1 回だけリトライ。
- **SSO / SAML コールバック**: `src/app/sso/callback/page.tsx` 等のクライアントページが
  PKCE コンテキスト(`code_verifier` / `state` / `nonce`)を sessionStorage から復元・検証し、
  `/auth/session/sso/login`・SAML セッションログインへ POST。コード交換とアサーション検証は
  従来どおり**バックエンド側**で行われる。

- Next.js サーバ専用の内部向け変数(`BACKEND_API_URL`、Cookie 属性系の `NEXT_PUBLIC_*` など)が消滅し、
  公開可能な `VITE_*`(API の URL 等)のみが残った。**フロント env に秘匿情報・内部トポロジ情報が残らない**。
- Cookie の名前・SameSite・Secure・CSRF・origin ポリシーの管轄が、フロント env から
  **バックエンド settings(`AUTH_*`)へ一元化**された。
- docker-compose 各種はポート 3000(Node)→ 8080(nginx / Vite dev)へ、ヘルスチェックは
  `/api/health`(Next route)→ nginx `/health` へ変更。unified 構成では非特権 nginx で起動する。
- 注意: SPA の `VITE_*` は**ビルド時に焼き込まれる**ため、環境ごとの切替はビルド引数
  (`FRONTEND_ENV_FILE`)または同一オリジン配置(`VITE_API_BASE_URL=/api/v1`)で行う。

## 5. 移行によるメリットと新たな留意点

### 5.1 アーキテクチャ面のメリット

1. **認証の「正」が 1 か所になった**: トークン発行・保管ポリシー・CSRF・失効の全てを
   FastAPI が所有する。以前は「FastAPI が発行 → Next.js が Cookie 化・検証」と責務が 2 分割され、
   同じ関心事(Cookie 属性、CSRF)の実装が 2 言語に分散していた。
2. **BFF ホップの消滅**: ブラウザ → Next.js → FastAPI の 2 段通信が 1 段になり、
   障害点・レイテンシ・デバッグ対象が減った。API 追加のたびに書いていた
   プロキシ route handler(todos/users で 5 ファイル)が不要になった。
3. **フロントエンドの純化**: フロントは「ビルド成果物(静的ファイル)」となり、
   フロントエンド技術の選択がバックエンド契約から完全に分離された(§7 参照)。

### 5.2 セキュリティ面の評価

**維持・強化された点**

- トークンは移行前と同じく **httpOnly Cookie** に保管され、XSS でトークンを窃取できない性質は維持。
  (SPA 移行でしばしば発生する「localStorage にトークンを置く」退行を回避している)
- CSRF 対策は Next.js 独自実装から、**HMAC-SHA256 署名付き double-submit 方式**
  (`libkoiki/core/csrf.py`)へ移り、フレームワーク層のテスト付き共通実装になった。
- 既存の更新系エンドポイント(users)にも Cookie 認証時のみ発動する CSRF 検証が追加された。
- refresh はローテーション付き(`enable_rotation=True`)で、失敗時は Cookie を確実に破棄。
  logout は単一 refresh token を失効させる(`revoke_refresh_token` 新設)。
- フロントコンテナが非特権 nginx になり、フロント env から内部 URL・秘匿変数が消えた。

**新たに生じた留意点(運用・設計上の前提)**

- **ルートガードはクライアントサイドのみ**になった(旧 `middleware.ts` は削除)。
  これは防御の後退ではなく前提の明確化である — 本 FW はもともと
  「認可は必ずバックエンドのエンドポイントで強制する」(`docs/agent/auth-security.md`)設計で、
  UI 側ガードは利便性のためのものに過ぎない。ただし**この前提を破る実装(バックエンド認可の省略)が
  今後入らないこと**が従来以上に重要になった。
- **CORS + Cookie の設定精度が可用性・安全性に直結**する。クロスオリジン配置では
  `BACKEND_CORS_ORIGINS` の厳密一致、`AUTH_COOKIE_SAMESITE=none` + `AUTH_COOKIE_SECURE=true` が
  必要になる。本番は同一オリジン配置(`/api/v1` 相対パス)が最も安全な既定。
- PKCE の `state` / `code_verifier` はブラウザ(sessionStorage)保持となったが、
  コード交換・署名検証というセキュリティ本体はバックエンドにあり、これは標準的な
  SPA + Authorization Code Flow (PKCE) の構成どおり。

### 5.3 実装量・保守面のメリット

- フロントの自前サーバコード(route handlers / middleware / cookie / csrf ユーティリティ)
  約 1,800 行を削除し、SPA 起点コード約 270 行で置換。差引き約 1,500 行の削減。
- 依存ツリーが大幅に縮小(package-lock −2,200 行超)。Next.js のバージョン追従・
  セキュリティパッチ対応という保守負担が消えた。
- 一方でバックエンドには約 1,550 行(実装 ~700 + テスト ~840)が増えたが、
  これは**どのフロントエンド技術からも再利用できるフレームワーク資産**として `libkoiki` に蓄積された。

## 7. 初心者向け解説: KOIKI-FW の根幹 — フロントエンド技術に拠らない FastAPI Web アプリ基盤

このプロジェクトに初めて触れる方へ。今回の「Next.js から React への乗り換え」という出来事は、
実はこのプロジェクトの**いちばん大事な設計思想**を理解する絶好の教材です。

### Web アプリは「画面」と「中身」でできている

Web アプリケーションは大きく 2 つの部分でできています。

- **フロントエンド**: ブラウザに表示される画面。ボタンや入力フォームなど、目に見える部分。
- **バックエンド**: データの保存、ログインの確認、業務ルールの実行など、目に見えない中身。

KOIKI-FW の根幹は後者、**Python の FastAPI で作られたバックエンド基盤**です。
ユーザー管理、ログイン、権限チェック、データベース操作、セキュリティ監視といった
「どんな業務アプリにも必要な土台」が、再利用できる形で `components/libkoiki/` に整備されています。

### 「API」という約束ごとでつながる

では画面と中身はどうやって会話するのでしょうか。KOIKI-FW では **API(Application
Programming Interface)** という「約束ごと」だけでつながります。たとえば:

> 「`/api/v1/auth/session/login` にメールアドレスとパスワードを送れば、
> ログインを確認して、以後の通行証(Cookie)を発行します」

バックエンドはこの約束(API 契約)を守ることだけに責任を持ち、
**画面がどんな技術で作られているかを一切知りません**。相手が Next.js でも、React でも、
スマホアプリでも、curl コマンドでも、約束どおりに呼べば同じように応えます。
これが「**フロントエンド技術に拠らないアーキテクチャ**」の意味です。

### 今回の移行がその証明になった

今回のブランチでは、フロントエンドを Next.js から React SPA へ**全面的に作り替え**ました。
もしバックエンドが特定のフロントエンド技術に依存した作りだったら、
バックエンドも大改修になっていたはずです。

実際に起きたことはこうでした:

- 既存の API は **1 本も削除・変更されていない**。
- バックエンドの変更は「ブラウザから直接使いやすい新しい玄関
  (Cookie セッション方式のログイン API)を**追加した**」ことだけ。
- ログイン確認や権限チェックの本体ロジックは 1 行もコピーせず、新旧の玄関で共有。

つまり、**画面側を丸ごと入れ替えても、中身は「入口を 1 つ増やす」だけで済んだ**のです。
これは偶然ではなく、「バックエンドは API という約束ごとだけを公開し、
フロントエンドの事情を持ち込まない」という設計を守り続けてきた結果です。

### 覚えて帰ってほしいこと

1. KOIKI-FW の本体は **FastAPI による API 志向のバックエンド基盤**(`components/libkoiki/`)である。
2. フロントエンド(`frontend/`)は API の「利用者の一人」にすぎず、技術は交換可能である。
3. セキュリティ(ログイン、権限、CSRF 対策)は**必ずバックエンドで**強制する。
   画面側の出し分けは利便性のためであって、防御ではない。
4. 将来、別の画面技術・モバイルアプリ・外部システム連携が必要になっても、
   同じ API 契約に接続すればよい — それがこの基盤の価値である。
