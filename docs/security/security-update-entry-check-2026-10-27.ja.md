点検日: 2026-10-27（日本時間）。対象ブランチ: `security/backend-python-emsign-brotli`。点検元コミット: `ac82bb3`。

## 1. 結論と実施範囲

**当初のCVEを起点とする対応計画になっている。バックエンドT2（取得ツール・CA準備）とフロントエンドF0（更新前動作テスト）へ着手できる。** ただし、これは両タスクが完了したことや、Dockerビルド・本番配備まで全て準備済みであることを意味しない。

本点検は提案・設計・デルタSpec・タスク・現ファイル・保存済み証拠を照合し、着手手順を補完したもの。新たな公式情報の再検索、テスト本体の実行、依存インストール、CA差し替え、Docker／CI設定の実装は行っていない。

## 3. 今回見つけて補完した点

1. T2は「方法の確定」だけで完了するようにも読めたため、隔離ツール実体の準備・ハッシュ確認・CA判定・結果記録までを子タスクに分けた。
2. F0の「現行環境」と計画上のNode22系を分けた。現ホストはNode24.19.0／npm11.9.0。現在導入されたfrontendの直接依存はロックの版と一致し、テスト7ファイルが存在する。ただし全間接依存の一致、テスト成功、警告の有無はF0で確認する。
3. backendの `docker/certs/nscacert.pem`、frontendの `frontend/docker/certs/nscacert.pem` は現在未配置。DockerfileがCOPYするため、このままのDockerビルドは失敗する。CAの必要性・正規の提供元・注入方式はT2で確認する。偽のCA、無関係なホストCAの流用、空ファイル、TLS検証無効化で通さない。
4. 両計画へ本書の着手条件を紐付けた。独自CAと完成イメージ・実IdP試験などの未検証事項を完了扱いしない。

## 4. バックエンドT2の実行単位

入力: 採用版記録、保存した公式ハッシュ、最新の配布証拠、更新前監査。出力保存先の例はリポジトリ外の `../work/backend-security-t2/`。秘密値はコミットしない。

- **T2.1 同定**: OS／CPU、現在のPython／pip／uv、各CA参照先と既存ロックのハッシュを記録する。ホストのtrixieと目標コンテナのbookwormを混同しない。
- **T2.2 検証済み配布物**: pip26.2.2、uv0.13.5、certifi2026.10.23の対象プラットフォーム向け配布物を作業領域へ取得し、採用版記録のハッシュを照合する。採用版変更が必要なら先に根拠を更新する。
- **T2.3 隔離した取得ツール**: 既存アプリの.venvを変更せず専用ツール環境へ導入し、ツールの実行パス・版・内蔵CAを確認する。古いbootstrap pipを使う場合も、ハッシュ検証済みローカルwheelを `--no-index` で導入し、旧環境から無検証でオンライン更新しない。
- **T2.4 CA準備**: OS／追加CAの信頼元を確認する。独自CAが必要なら管理された正規のCAを取得し、公開証明書だけを現環境へ安全に注入する。不要な環境で必須COPYを解消する変更が必要なら、その方式を設計に追記してから実装する。セッション用proxy CAは実行環境の指示に従いmountし、プロジェクトの社内CAと混同しない。
- **T2.5 判定記録**: 正規TLSの確認、参照CA、取得元／ハッシュ、準備したツールの版と未解消項目を記録する。ネットワーク接続不可やCA未確認は、影響する作業を待機として残す。

**T2完了条件**: 隔離ツールが予定版で実行でき、取得経路と信頼ストアの確認結果・独自CAの注入方針が記録されていること。Dockerをビルドする前には、必要なCAそのものの配置または合意した代替注入の実装が必要である。CAが未入手でもT2の調査・配布物準備は進めるが、CA依存の通信・ビルドを完了扱いしない。

T2でroot／componentの依存定義やuv.lock、アプリ.venvは変更しない。ツール環境のPythonが旧版である場合は記録し、Pythonのssl対策を適用済みとしない。T3は準備したツール・CAを使い、Pythonだけの変更を旧アプリロックで比較する。

## 5. フロントエンドF0の実行単位

出力保存先の例は `../work/frontend-security-baseline/`。次の段階はF0であり、Node／package.json／package-lockの更新ではない。

- **F0.1 同定**: Node／npmのパス・版・OS、frontendのmanifest／lockのハッシュ、導入依存の一覧を記録する。`npm ls --all --json` 等で不足・差異を調べ、非ゼロ終了は結果を読んで分類する。
- **F0.2 実行条件**: 既存node_modulesが利用可能なら依存同期をせず現状の基準を取る。現Node24.19.0は採用目標22系とは別の更新前環境として記録する。信頼できないBrotli応答・archiveの取得、外部サービスへの接続を検証に混ぜない。テストのMSWは未定義リクエストをエラーにする設定である。
- **F0.3 基準コマンド**: frontend/で `npm run check-types`、`npm run lint`、`npm test`、`npm run build` を別々に実行し、各終了コード・標準出力・標準エラーを保存する。テスト件数・スキップ・失敗・警告を整理する。
- **F0.4 再確認**: lock／manifestのハッシュが不変かを確認し、未実行・環境起因の失敗と機能退行を区別する。buildで生成されたdist等は基準成果物として管理し、ソース変更として混ぜない。

node_modulesが欠損・不一致の場合は、その状態で全件成功とは扱わない。修正版Nodeを作業領域に隔離して現行ロックのクリーン再現を行う方法を選び、再現用の実行環境を変更した事実を記録する。プロジェクトの採用設定変更はF1、依存版変更はF3で行う。npm ciは依存のライフサイクルスクリプトも実行し得るため、正規レジストリ・integrity・必要なスクリプトを確認してから再現する。

**F0完了条件**: 4コマンドを実行して結果が保存され、比較用の依存版・環境・成功／失敗・警告とハッシュが特定されていること。既存不具合があれば基準として記録し、更新後の比較方法を確定する。失敗を隠して基準取得済みとしない。

F0はDockerを使わずに着手できるため、未配置の独自CAやKeycloakの取得エラーはF0を止めない。SSO／SAMLの実IdP合同試験はF6で行い、F0の成功で代替しない。

## 6. 進行と残件

T2とF0は相互の完了待ちが不要。Codexは各タスク内で調査・準備・実行・切り分け・記録を進め、重大な採用方針変更・API契約変更・リスク受容は判断を記録して相談する。Dev Container変更はPython側とNode側で同じファイルを触るため実装差分を調整する。

Keycloak、完成アプリ／Dev Container、配備CPU全種、独自CA、実IdP接続、既存OSS37指摘／npm18パッケージの最終判定は残件。これらは次工程への着手と全体完了の判定を分けて扱う。今回、T2やF0の実行済みチェックは付けていない。
