# Requirement Patterns

実装Spec種別ごとに「どの Requirement を立てるか」の骨格を示す。D-03 第6章の記述項目を Requirement 単位に読み替えたもの。

記法そのものは `SKILL.md` を参照する。ここでは **何を Requirement として切り出すか** だけを扱う。

---

## 機能Spec（`openspec/specs/<capability>/spec.md`）

capability 全体に効く業務ルールのみを Requirement にする。個別の実装に閉じる振る舞いは書かない。

セクション構成：

```
# <機能名（日本語）>（<capability名>）
## Purpose            ← 50字以上。HTMLコメントを残さない
## 業務処理概要        ← なぜ存在するか / 誰が何のために使うか
## 業務目線の入出力
## 基本情報            ← capability名 / 番台対応 / 主なレイヤ
## Requirements       ← 最低1つ必要
```

立てる Requirement の例：

- 申請期限・受付可能期間
- 金額上限・件数上限
- 必要書類の充足条件
- 業務ステータスの遷移規則
- 法令上の保持義務

**作成タイミング：** D-02 ①要件定義ステップで手で作成する。archive を待たない。この結果、以後の change は OpenSpec 上つねに Modified Capabilities として扱われる。

---

## 共通機能Spec

複数の機能Specから参照される共通処理。

| 立てる Requirement | 中身 |
| --- | --- |
| `<共通処理名>の呼び出し契約` | 適用スコープ（参照する capability 名）を冒頭に列挙。入力・出力の表 |
| `<共通処理名>の制約条件` | 性能・セキュリティ・データ整合性。計測条件と数値を明示 |

Scenario：正常系 / 異常系 / 境界値、および制約の計測条件ごとに1つ。

---

## API連携Spec

API エンドポイント。内部サービス間呼び出し・BFF にも流用する。

| 立てる Requirement | 中身 |
| --- | --- |
| `<API名>の受付` | パス・HTTPメソッド・認証認可方式の表。受理する条件 |
| `<API名>の入力検証` | バリデーションルールの表。ルールが少なければ受付Requirementに統合してよい |
| `<API名>の応答性能とレート制限` | 計測条件つきの性能値・レート上限 |

Scenario の目安：

- 正常系 - 必須項目充足
- 異常系 - 必須項目の欠損（400）
- 異常系 - 認証エラー（401）
- 異常系 - 認可エラー（403）
- 境界値 - 上限値ちょうど
- レート制限の超過（429）

エラーコード一覧は表にせず、**エラーコードごとに1 Scenario** に分解する。

## データ・DB Spec

| 立てる Requirement | 中身 |
| --- | --- |
| `<エンティティ論理名>の識別子` | 物理名・論理名・主キー。一意性 |
| `<エンティティ論理名>の業務データ項目` | 業務上の意味を持つカラム群。多い場合はさらに分割 |
| `<エンティティ論理名>の参照整合性` | 外部キーと業務的意味 |
| `<エンティティ論理名>のデータ保持` | 削除方式・保持期間・アーカイブ。法令要件があれば明記 |

**カラム定義表は意味単位で分割する。** 全カラムを1つの Requirement に詰めると500字を超え、レビューでも読めない。

**インデックス方針は書かない。** 実装方式に属するため `design.md` へ回す。

---

## 外部サービス連携Spec

| 立てる Requirement | 中身 |
| --- | --- |
| `<連携先サービス名>との連携` | 連携先・通信方式・認証方式の表。接続先の管理方法 |
| `<連携先サービス名>の障害時の振る舞い` | タイムアウト閾値・リトライ回数・バックオフ方式・冪等性 |

Scenario の目安：

- 正常系
- 異常系 - 業務エラー応答
- タイムアウト発生時
- リトライによる回復
- 連続失敗時（サーキットブレーカー）
- **冪等性の保証** — リトライを定義した以上、副作用が1回だけであることの検証が必ず必要になる

シークレットの値そのものは書かない。管理方針のみ記述する。

---

## セキュリティ横断Spec

特定の機能Specに閉じない横断要件。機能単位のセキュリティ要件は各実装Spec単位の制約条件Requirementに書く。

| 立てる Requirement | 中身 |
| --- | --- |
| `認証・認可の共通基準` | 適用スコープを冒頭に明示。認証方式・権限モデル・セッション有効期間 |
| `入力検証の共通基準` | 検証方法・サニタイズ |
| `保存データと通信の保護` | 暗号化方式・TLSバージョン |
| `監査ログの記録` | 記録対象操作・必須ログ項目・保持期間の表。マスキング |
| `実装上の禁止事項` | 【SHALL NOT】のみで構成。1行1件 |

`実装上の禁止事項` は `grep '【SHALL NOT】'` で案件横断に集計できる。禁止事項は必ずこの Requirement に集約し、他所に散らさない。

---

## 画面・UI Spec

利用者に提示される画面の振る舞い。API契約は API連携Spec に委ね、ここでは消費側の振る舞いのみを定義する。

| 立てる Requirement | 中身 |
| --- | --- |
| `<画面名>の表示` | 目的・利用者・表示項目の表・権限による表示差分 |
| `<画面名>の状態と遷移` | 初期表示／読込中／データなし／エラー／権限不足。状態ごとに1 Scenario |
| `<画面名>の入力と検証` | 入力項目と検証規則の表。クライアント側検証は事前提示であり実施ではない |
| `<画面名>の更新後の反映` | 更新操作後に何が最新化されるか。実現手段は design.md |
| `<画面名>のエラー表示方針` | 通信エラー／認証切れ／権限不足／業務エラーを区別 |
| `<画面名>の制約条件` | 対応環境・応答性（プロジェクトが定める場合のみ。定めがなければ Requirement ごと削除する） |

**必ず含める禁止事項：**

- 【SHALL NOT】画面上の非表示・活性制御・遷移制限を、認可の実施手段として用いてはならない
- 【SHALL NOT】クライアント側の検証を、入力検証の実施手段として扱ってはならない
- 【SHALL NOT】システム内部の情報（スタックトレース・内部識別子・接続先情報）を利用者へ提示してはならない

消費するAPIは、各 Requirement 本文に `消費するAPI：SPEC-<番号> <Requirement名>` の形式で明記する。

**design.md へ回すもの：** コンポーネント分割／状態管理・データ取得ライブラリの選定／ルーティング実装／スタイリング／キャッシュ無効化の実装手段。

「更新後の反映」の切り分けが本種別で最も判断を要する。**利用者から見た「更新後に一覧が最新化される」はSpec**、**どの仕組みでキャッシュを無効化するかは design.md** である。

## proposal.md（全種別共通）

```
# <実装Spec種別>：<名称>（<change-name>）
## メタ情報        ← change-name / 所属機能Spec / 実装Spec種別 / Spec番号 / 対象レイヤ / Harvest候補フラグ
## Why            ← 50字以上1000字以内
## What Changes
## Capabilities   ← New / Modified。機能Specが既存なら通常 Modified のみ
## Impact         ← レイヤ横断の波及があれば明記
```

共通ヘッダーはデルタSpecではなく **proposal.md に置く**。デルタSpecに置くとパーサ構造から外れ、archive 時に失われる。
